# パスワード機能の点検 — 0.5.1（2026-11-03）

今回行ったのは、実装の読み直しと回帰テストによる点検です。第三者による独立した監査・侵入テスト・安全性の認証ではありません。

## 補強した箇所

| 対象 | 対策と検証 |
|---|---|
| ロック解除済みMacでの保存情報の使用 | アカウント選択後、毎回OSのTouch IDを要求。成功した場合だけ選択した情報を取得し、入力する。認証の成功は共有・キャッシュしない。 |
| キャンセル・失敗・Touch ID非対応 | 入力しない。認証なしに切り替える経路や、アプリがMacのパスワードを集める画面は設けない。 |
| 既存情報の更新・削除 | 確認ダイアログに加えてTouch IDを要求。認証が完了しなければ既存データを維持する。 |
| 認証待ちの間の対象変更 | サイト移動、タブ・スペースの切り替え（戻した場合を含む）、画面ロック・スリープ・ユーザー切り替えで操作を無効化。認証後と情報取得後に再照合する。 |
| 入力欄の差し替え | origin、ページURL、フレーム、ナビゲーション世代、フォーカス、入力欄の参照・属性・用途・表示状態・フォーム送信先を照合。通常のinput/changeイベントを発行し、自動送信しない。 |
| 保存データ | MacのsafeStorage非同期APIで全体を暗号化。0600の一時ファイルから原子的に入れ替える。暗号化不可・破損・書込失敗時に平文や空のデータへ切り替えない。 |
| 外部サイトからのアプリ操作 | sandbox、contextIsolation、webSecurityを維持。外部ページにNodeや操作APIを公開しない。隔離されたsandbox preloadから固定チャネルで送られるログイン候補は、最上位フレーム・origin・タブ・スペース・長さを検証し、保存前にネイティブ確認する。ローカルUIと候補Viewの送信者・フレーム・URLも検証する。 |

## 残る制約

- Touch IDはアプリ内の操作を制限するもので、暗号鍵そのものに利用者の在席確認を付与した構成ではない。MacのsafeStorageによる保護は継続するが、Portioのプロセスやアプリ自体を侵害された場合まで防ぐものではない。
- 候補・管理一覧の表示時には暗号化ファイルを読み、アカウント名を表示する。Touch ID前の一覧表示は許可している。保存データ全体の復号はメインプロセス内で行い、パスワードを一覧へ返さない。
- 入力後のパスワードは対象サイトから読める。サイト内の悪意あるスクリプトや、同一サイトの侵害を検知・防止する保証はない。
- ログイン済みタブ、Cookieによる既存のセッション、手入力済みのフォームはこの本人確認の対象外。共有利用時はMac自体をロックする必要がある。
- Touch IDのない／未設定のMacでは保存情報による入力・更新・削除ができない。Macのパスワードによる代替認証は未実装。保存形式は0.5.0から変更せず、認証が使えないことを理由にデータを削除しない。
- 自動更新、Apple Developer ID署名・公証は未実施。更新時にOSがキーチェーンの許可を求める可能性がある。OSの許可は利用者が判断する。
- 実在アカウント、全サイトのフォーム、OSや暗号鍵の移行、侵入テストは対象外。実機確認と自動テストの区別は[TESTING.md](../TESTING.md)に記録する。

## 依存部品の確認

2026-11-03の`npm audit`はmoderate 5件（glob/minimatchからpackager系に波及）、high/critical 0件。これらはアプリ作成時の開発用依存で、作成したアプリに含めない。ビルドへ未信頼のファイル・パターンを渡さず、修正版を取り込める更新時に再確認する。重大版のダウングレードを伴う自動修復は行っていない。これはElectron・Chromiumの全脆弱性がないことを示すものではない。
